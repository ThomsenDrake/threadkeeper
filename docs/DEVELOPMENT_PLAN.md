# Autonomous MVP development

The user's standing direction is to develop the full Threadkeeper application autonomously, including merging the session's own PRs after the GitHub `@codex review` loop. A broad request to continue development means implementing the remaining MVP, choosing the next useful feature, and continuing across reviewable increments. A narrower explicit request still controls its task. [AGENTS.md](../AGENTS.md) defines execution and merge conditions; [MVP_BRIEF.md](MVP_BRIEF.md) defines the product.

## Delivery loop

1. Select the highest-value unblocked outcome and define a small observable acceptance flow. Make routine implementation and interface decisions from the existing product requirements. Ask only for consequential missing decisions or access that cannot be inferred and actually blocks the next action.
2. Implement a complete vertical feature in a `codex/` branch: shared contracts, database rules, API/MCP, worker and profile as required. Delegate independent implementation, inspection or validation to subagents when useful. Keep the product personal context for existing clients; a general assistant and task manager remain outside scope.
3. Run `pnpm check`, the relevant synthetic demonstrations and checks appropriate to the affected paths. Use native/full-stack integration when available and relevant, and browser verification for user-facing changes. A documentation-only change needs documentation checks rather than an unnecessary full application test run. Avoid repeated broad testing once it passes unless further changes or failures justify it. Include implemented behavior, actual verification and remaining limits in docs/HANDOFF.md before submitting the PR for final review.
4. Open a reviewable PR. Request `@codex review`, read its actual result, address actionable findings, verify changes and request review of the final commit. Explain evidence-backed disagreements rather than blindly changing correct code. A locally spawned reviewer supplements the requested GitHub review; it does not replace it for self-merge eligibility.
5. Merge the session's own PR only when the latest head is reviewed, actionable findings are resolved, required checks/approvals are satisfied and no merge conflict remains. Guard the merge against a changed head SHA. Do not bypass repository protection. For a stacked PR, wait for prerequisites to merge, update/retarget to main and obtain review of the resulting head before self-merging; do not merge into another task's branch. If final review or required checks are blocked, leave that PR ready or explicitly blocked and continue independent work.
6. Update from main, refresh the working plan and choose the next unblocked feature. Include any subsequent handoff edits in the next reviewed branch. Keep PRs coherent; do not accumulate the entire app into one oversized diff merely to avoid checkpoints. A merged PR is an intermediate delivery point in a broad task.

## External dependencies and stopping

Use existing authorized provider settings without exposing secrets. If credentials, GPU hardware or installed MCP hosts are unavailable, finish all product work that can be exercised independently. Keep deterministic fixtures as test support and keep real-provider checks separate; fixture success does not establish semantic quality or self-hosted GPU compatibility. Never silently substitute another memory model. The exact Nemotron default remains binding.

Real-model extraction/embedding evaluation and installed-client validation are release requirements. Run them when authorized configuration and capabilities are present. Missing external access should not turn every new task into another fixture or infrastructure project while the profile and client workflows remain unfinished.

Stop a broad development task when the MVP acceptance criteria are implemented and available verification is complete, the user redirects the work, or no meaningful authorized work remains unblocked. Complete independent work before reporting a blocker. Record current branches/PRs, concrete missing access or decisions, verified outcomes, remaining release gates and the next executable action. If a runtime limit ends work early, leave an honest partial handoff; do not call the app complete because the test harness passed. Context compaction and completion of an individual subtask do not end the objective.

Self-merging permission does not authorize deployment, DNS changes, paid resources, public publication/license selection or reusable Cloud environment changes. Those boundaries remain unchanged. Do not create or schedule new user-owned tasks without a request.
